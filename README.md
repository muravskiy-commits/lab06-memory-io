Відповіді на питання:
1. Які addresses розташовані близько одна до одної? Адреси function (.text), initialized global (.data), static (.data) та uninitialized global (.bss) розташовані поруч у нижній частині адресного простору (відрізняються лише молодшими байтами в межах кількох кілобайт).

3. Чи stack знаходиться в іншій області? Так, локальна змінна розташована у значно вищих адресах (0x7ffc... / 0x7ffd...), відокремлених великим невідображеним проміжком від купи.
4. Чи addresses однакові між різними запусками? Ні, базові адреси сегментів змінюються при кожному запуску через роботу механізму ASLR (Address Space Layout Randomization). Усі виведені значення є віртуальними адресами (virtual addresses), а не фізичними адресами в RAM.

Завдання 4. Heap складається з Virtual Memory (heap_growth.c)

Порівняння показників /proc/PID/status до і після заповнення 100 МБ пам'яті:

| Стан програми | VmSize (віртуальна пам'ять) | VmRSS (фізична RAM) |
| :--- | :---: | :---: |
| Одразу після malloc(100 MB) | ~105 160 kB | ~1 540 kB |
| Після циклу запису memory[i] = 1 | ~105 160 kB | ~103 940 kB |

Висновок:
Виклик malloc(100 MB) лише резервує діапазон віртуальних адрес у таблиці сторінок процесу (зростає VmSize), але ядро Linux не виділяє фізичні кадри RAM миттєво (VmRSS залишається малим). Реальна фізична пам'ять виділяється ліниво (demand paging): коли програма вперше звертається на запис до кожної 4096-байтної сторінки, виникає minor page fault, і ядро прив'язує віртуальну сторінку до вільного фізичного кадру RAM.

Завдання 5 та 6. Invalid Memory Access (invalid_memory.c)

Фрагмент виводу strace ./invalid_memory:
write(1, "About to access invalid memory\n", 31) = 31
--- SIGSEGV {si_signo=SIGSEGV, si_code=SEGV_MAPERR, si_addr=NULL} ---
+++ killed by SIGSEGV (core dumped) +++

Відповіді на питання:
1. Чому OS не дозволяє process просто записати за address 0? Нульова сторінка (адреса 0x0 / NULL) навмисно залишається невідображеною (unmapped) у таблиці сторінок процесу, щоб миттєво перехоплювати помилки розіменування неініціалізованих або нульових вказівників.
2. Як це захищає систему? Апаратний блок керування пам'яттю (MMU) перевіряє кожне звернення до пам'яті за правами доступу в таблиці сторінок; при спробі доступу до чужої або невідображеної адреси генерується виняток (page fault), і ядро завершує лише порушника сигналом SIGSEGV, не зачіпаючи інші процеси та саме ядро.
3. Чи означає Segmentation fault фізичну поломку RAM? Ні, це механізм логічного та апаратного захисту віртуального адресного простору, а не несправність мікросхем пам'яті.

Завдання 9 та 10. write() та read() (write_file.c, read_file.c)

Аналіз потоку даних у write(fd, message, strlen(message)):
1. Де знаходиться message? У віртуальному адресному просторі процесу (на стеку функції main).
2. Що означає fd? Індекс відкритого файлу в таблиці дескрипторів процесу, через який ядро знає, у який файл записувати дані.
3. Що означає size? Кількість байтів, яку програма просить скопіювати з буфера процесу у файл (19 байтів).
4. Що повертає write()? Кількість фактично записаних байтів (19) або -1 у разі помилки.

Значення, які повертає read(fd, buffer, sizeof(buffer)):
- > 0: кількість реально прочитаних байтів у буфер;
- 0: досягнуто кінця файлу (EOF — End of File);
- -1: помилка читання (код помилки зберігається в errno).

Завдання 11 та 12. File Offset та lseek() (file_offset.c)

Результат виконання file_offset.c на файлі input.txt ("Computer Systems\nOperating Systems\n"):
First:  [Compu]
Second: [ter S]
After lseek(0): [Compu]

Пояснення:
1. Прогноз підтвердився: другий виклик read() не читає файл спочатку, оскільки ядро зберігає поточну позицію читання/запису (file offset) у системній таблиці відкритих файлів і автоматично зсуває її на кількість прочитаних байтів (із 0 на 5).

3. Sequential access (послідовний доступ) — читання або запис даних підряд від початку до кінця з автоматичним просуванням зміщення. Random access (довільний доступ) — переміщення вказівника позиції в довільне місце файлу за допомогою lseek() без необхідності читати проміжні дані.

Завдання 15 та 16. printf() проти write() та роль fflush() (buffering.c)

Без fflush(stdout):
- Вивід у термінал: DABC (або на початку файлу записується D, а ABC скидається пізніше при завершенні програми).
- У trace системних викликів write(1, "D", 1) виконується раніше, ніж write(1, "ABC", 3).
- Причина: функції бібліотеки stdio (printf) накопичують дані в буфері користувацького простору (user-space buffer) і не роблять системний виклик write() до заповнення буфера, символу нового рядка \n (для термінала) або завершення програми. Натомість write() одразу звертається до ядра.

Після додавання fflush(stdout) перед write():
- Trace системних викликів:
  write(1, "ABC", 3) = 3
  write(1, "D", 1)   = 1
- Вивід у термінал: ABCD.
- Роль fflush(stdout): примусово очищує буфер стандартного виводу stdio, негайно передаючи накопичені дані в ядро через системний виклик write() до того, як виконаються наступні низькорівневі операції виводу.

5. Фінальне завдання — file_copy.c

Перевірка роботи утиліти на текстових та бінарних даних:
- ./file_copy source.txt destination.txt -> cmp source.txt destination.txt повертає статус 0 (файли ідентичні).
- ./file_copy file_copy copy_of_file_copy -> cmp file_copy copy_of_file_copy повертає статус 0 (скомпільований бінарний файл скопійовано без втрат).

Чому один і той самий цикл read/write копіює і текст, і бінарні файли?
На рівні системних викликів POSIX немає поділу на «текстові» чи «бінарні» файли — будь-який файл є послідовністю сирих байтів, які циклічно зчитуються у байтовий масив char buffer[4096] і без інтерпретації записуються у цільовий дескриптор (з урахуванням циклу обробки partial write).

Фрагмент strace -e trace=openat,read,write,close ./file_copy source.txt destination.txt:
openat(AT_FDCWD, "source.txt", O_RDONLY) = 3
openat(AT_FDCWD, "destination.txt", O_WRONLY|O_CREAT|O_TRUNC, 0644) = 4
read(3, "Operating Systems\nComputer Archi"..., 4096) = 40
write(4, "Operating Systems\nComputer Archi"..., 40) = 40
read(3, "", 4096)                       = 0
close(3)                                = 0
close(4)                                = 0

Повна схема Data Path під час роботи file_copy:

SOURCE FILE (диск / файлова система)
     |
     | read(3, buffer, 4096) -> системний виклик у Kernel
     v
==========================================
     Kernel (Page Cache / VFS)
==========================================
     | копіювання байтів у user-space через MMU
     v
Process Virtual Memory: char buffer[4096] (Stack)
     |
     | write(4, buffer, 40) -> системний виклик у Kernel
     v
==========================================
     Kernel (Page Cache / VFS)
==========================================
     |
     v
DESTINATION FILE (диск / файлова система)

Інтеграційне пояснення ланцюжка char buffer[4096]; read(fd, buffer, sizeof(buffer));:
Програма виділяє на стеку масив buffer, адреса якого є віртуальною адресою в адресному просторі процесу, і передає її разом із файловим дескриптором fd у системний виклик read(). Перетнувши межу user-space / kernel-space, ядро за номером fd знаходить відкритий файл у таблиці дескрипторів процесу, зчитує дані з файлової системи та через таблицю сторінок і апаратний MMU відображає віртуальну адресу буфера у відповідний фізичний кадр пам'яті (page frame), записуючи туди прочитані байти.

6. Відповіді на контрольні питання

1. Що таке virtual address? Адреса пам'яті в ізольованому віртуальному адресному просторі процесу, яку бачить програма і яка транслюється у фізичну адресу апаратним MMU.
2. Чим virtual address відрізняється від physical address? Віртуальна адреса існує лише в межах конкретного процесу, тоді як фізична адреса вказує на реальну комірку мікросхеми оперативної пам'яті (RAM).
3. Що таке virtual address space? Безперервний діапазон віртуальних адрес, виділений операційною системою для одного процесу (код, дані, купа, стек, бібліотеки).
4. Чому два processes можуть використовувати однакову virtual address? Тому що кожен процес має власну таблицю сторінок (page table), і MMU відображає однакову віртуальну адресу різних процесів у різні фізичні кадри RAM.
5. Що таке page? Фіксований за розміром блок віртуального адресного простору (зазвичай 4096 байтів).
6. Що таке page frame? Фіксований блок фізичної оперативної пам'яті (RAM) такого ж розміру, як і віртуальна сторінка (4096 байтів).
7. Що таке page table? Структура даних ядра для кожного процесу, яка зберігає відповідність між номерами віртуальних сторінок (VPN) і номерами фізичних кадрів (PFN), а також прапорці прав доступу.
8. Яку роль виконує MMU? Memory Management Unit — апаратний блок процесора, який на льоту перекладає віртуальні адреси у фізичні за таблицею сторінок і перевіряє права доступу.
9. Що таке TLB? Translation Lookaside Buffer — швидкий апаратний кеш всередині CPU/MMU, що зберігає нещодавні переклади віртуальних сторінок у фізичні кадри для прискорення доступу до пам'яті.
10. Чим TLB miss відрізняється від page fault? При TLB miss потрібний запис відсутній у кеші TLB, але є в page table у пам'яті (апаратний обхід таблиці); при page fault віртуальна сторінка взагалі не прив'язана до фізичного кадру або порушено права доступу, що вимагає втручання ядра ОС.
11. Що таке page fault? Виняток процесора при зверненні до віртуальної сторінки, яка наразі не відображена у фізичну пам'ять або захищена від даного типу доступу.
12. Чи page fault завжди означає помилку програми? Ні. Minor page fault є штатним механізмом лінивого виділення пам'яті (наприклад, після malloc()), а major page fault — підвантаженням сторінки з диска. Помилкою є лише invalid page fault (наприклад, звернення до NULL).
13. Як virtual memory допомагає ізолювати processes? Процес фізично не може сформувати адресу, яка не відображена в його власній page table, тому він не здатний прочитати чи пошкодити пам'ять іншого процесу або ядра.
14. Що означають r, w, x у memory mappings? Права доступу до регіону пам'яті: r (read — читання), w (write — запис), x (execute — виконання інструкцій).
15. Чому code не обов'язково повинен бути writable? Програма виконує інструкції з сегмента коду, але не змінює їх під час роботи; заборона запису захищає код від пошкодження та атак.
16. Чому malloc() не слід просто ототожнювати з негайним використанням такої ж кількості physical RAM? Через механізм demand paging ядро спочатку виділяє лише віртуальні адреси (VmSize), а фізичні кадри (VmRSS) надає поступово в момент фактичного запису у сторінки.
17. Що таке file descriptor? Невелике невід'ємне ціле число, яке ідентифікує відкритий файл, сокет або канал у таблиці відкритих файлів процесу в ядрі.
18. Чим pathname відрізняється від file descriptor? Pathname — це текстовий шлях до файлу у файловій системі, а file descriptor — числовий дескриптор уже відкритого потоку вводу/виводу в ядрі.
19. Що зазвичай представляють descriptors 0, 1, 2? 0 — стандартний ввід (stdin), 1 — стандартний вивід (stdout), 2 — стандартний потік помилок (stderr).
20. Що робить open()? Відкриває або створює файл за вказаним шляхом і повертає найменший вільний файловий дескриптор.
21. Що повертає read()? Кількість фактично прочитаних байтів (> 0), 0 при досягненні кінця файлу (EOF) або -1 у разі помилки.
22. Що означає read() == 0? Досягнуто кінця файлу (EOF), більше даних для читання немає.
23. Що повертає write()? Кількість фактично записаних байтів (може бути меншою за запитану) або -1 у разі помилки.
24. Чому потрібно враховувати partial writes? Системний виклик write() може записати лише частину буфера (через переповнення буферів ядра, сигнали або специфіку каналів/мережі), тому надійні програми викликають write() у циклі до повної передачі всіх байтів.
25. Що таке file offset? Поточна позиція в байтах від початку відкритого файлу, з якої почнеться наступна операція read() або write().
26. Для чого використовується lseek()? Для примусової зміни поточної позиції (file offset) у відкритому файлі (відносно початку, поточної позиції або кінця).
27. Чим FILE * відрізняється від file descriptor? File descriptor (int) — це низькорівневий ідентифікатор ядра для системних викликів POSIX, тоді як FILE * — це структура стандартної бібліотеки C (stdio), яка містить файловий дескриптор плюс буфер користувацького простору.
28. Чому printf() не обов'язково негайно викликає write()? Оскільки printf() використовує буферизацію stdio для зменшення кількості дорогих системних викликів і накопичує дані в пам'яті процесу до скидання буфера.
29. Що таке buffering? Тимчасове накопичення даних у проміжному буфері пам'яті перед їх фактичною передачею на пристрій або в ядро для підвищення продуктивності.
30. Що робить fflush()? Примусово скидає (записує) усі накопичені дані з буфера потоку stdio у ядро через системний виклик write().
31. Чому redirection > може працювати без зміни source code програми? Бо програма пише у фіксований дескриптор 1 (stdout), а оболонка shell перед запуском програми підміняє в таблиці дескрипторів ресурс, на який вказує номер 1 (замість термінала підключає файл).
32. Чому file_copy може однаково копіювати text та binary files? Бо системні виклики read() і write() оперують неструктурованими байтами без аналізу кодувань чи символів кінця рядка.
33. Де фізично/логічно знаходиться buffer під час read()? Логічно масив char buffer[4096] розташований у віртуальному адресному просторі процесу (на стеку), а фізично — у відповідному фізичному кадрі оперативної пам'яті (RAM), куди MMU транслює його віртуальну адресу.
34. Як file descriptor, virtual memory та system call взаємодіють під час I/O? Програма передає номер дескриптора та віртуальну адресу буфера у системний виклик; ядро за дескриптором знаходить файл, а через таблицю сторінок і MMU отримує доступ до фізичної пам'яті буфера процесу для безпечного копіювання даних.

---

7. Висновок
У ході лабораторної роботи було експериментально досліджено роботу віртуальної пам'яті та системного вводу/виводу в Linux. Підтверджено, що всі адреси в програмі є віртуальними та ізольованими для кожного процесу, фізична пам'ять під купу виділяється ліниво по сторінках розміром 4096 байтів при зверненні, а порушення прав доступу миттєво блокується через MMU та SIGSEGV. У другій частині роботи на практиці проаналізовано роботу файлових дескрипторів, зміщення файлу, буферизацію stdio та реалізовано надійне копіювання текстових і бінарних файлів через низькорівневі виклики POSIX з обробкою часткового запису.
